# SpiceDB clients: integration guide for AI coding agents

This guide is for AI coding agents (and the humans reviewing them) adding SpiceDB
authorization to an application. It answers two questions: **which library tier
to use**, and **how to integrate it without introducing authorization bugs**.
Each language directory has its own `AI_INTEGRATION_GUIDE.md` with concrete
code for that language, where one exists. When this guide and a language guide
disagree on an API name, the language guide wins.

The libraries are prototypes; pin a commit. Behavior described here is the
contract in [DESIGN.md](DESIGN.md).

## 1. Pick a tier

There are three tiers. Use the highest one that fits; drop down only for a
reason you can name.

| Tier | What it is | Use it when |
|---|---|---|
| **Typed** (generated by `spicedb-gen`) | Code generated from *your* `.zed` schema: `Document("readme").View()`, `Document("readme").Viewer(User("alice"))`. Wrong relations, permissions and subject types fail to compile. | The application owns a schema that is checked into its repository. **This is the default for application code** in Go, Python, TypeScript and Java. |
| **Idiomatic** (native client) | Schema-agnostic client with native types: `PermissionCheck`, `Relationship`, `Filter`, consistency strategies, typed errors. | The code must work with *any* schema (CLIs, admin tools, proxies, migration jobs), the language has no generator (C#, Ruby, Rust), or you need an operation the typed layer doesn't wrap (watch, import/export, schema, counters). In generated languages the typed client already exposes every native method, so you rarely construct both. |
| **Raw protocol** | The generated `authzed.api.v1` protobuf/gRPC stubs, reached through the native client's escape hatch (`RawProto`/equivalent). | Almost never. First try the native client's per-call transport options and response-metadata capture (headers, trailers) and its exported protocol conversions. |

### Decision rules

- **The schema is known at build time → typed.** Regenerate on every schema
  change and commit the generated file. Never hand-edit it.
- **Names arrive at runtime but come from that schema** (a permission per API
  route, a relation from config) → still typed. Use the generated **by-name
  lookups** (`PermissionByName`, `RelationByName`, `RelationshipByName`), which
  reject names and subjects the schema doesn't define, and verify the mapping at
  startup with the generated name lists. Don't fall back to string-built native
  requests.
- **The code is schema-agnostic → idiomatic.**
- **Raw → only through the escape hatch**, never by importing protocol packages
  to build requests yourself.
- **Never add a second copy of the protocol bindings.** Do not add a legacy
  `authzed-*` library (authzed-go, authzed-py, @authzed/authzed-node,
  authzed-java, the `authzed` gem) next to these clients, unless that legacy
  release has been bridged onto this repository's proto tier. Two copies of
  `authzed.api.v1` crash Go at startup and misbind in Python, Ruby and the JVM.
  Each client's `MIGRATION.md` explains how to move off its legacy library.

## 2. Integrate safely

### Checks

- **A check never returns a boolean.** Use the result's predicate
  (`HasPermission()` / `has_permission` / `hasPermission()`), never the object.
  Only an *unconditional* grant is true. *Conditional* means caveat context was
  missing: either pass the context and check again, or deny.
- **Fail closed.** On any error, including timeouts, deny the request. Never
  turn an error into a grant, and never cache an error as a decision.
- **Check many things at once with bulk checks**, not a loop of singular
  checks. Results come back in input order. In bulk checks with per-item errors
  enabled, an errored item is never a grant.
- **Listing what a user can see → LookupResources with the "has permission
  only" filter**, not "list everything, then check each". Without the filter,
  results include conditional matches that are *not* grants.
- **Check-time context ≠ stored caveat context.** Pass request facts (IP, time)
  as check context. Write caveat parameters that belong to the relationship
  when you write the relationship.

### Consistency (pick deliberately; every read requires one)

| Strategy | Use for |
|---|---|
| **minimize latency** | Most checks. Fastest; may read slightly stale data. |
| **at least as fresh as `token`** | Reads that must observe a specific write. Store the `ZedToken` from the write result (for example on the resource row whose access changed) and pass it here. This is the standard defense against the "new enemy" problem. |
| **fully consistent** | Rare, correctness-critical reads that have no token. Expensive; keep it out of hot paths. |
| **exact snapshot of `token`** | Several reads that must see the same instant. |

Keep tokens as the library's opaque `ZedToken` type. Persist them only with the
type's own string conversion.

### Writes

- **One logical change = one transaction.** Combine touches, creates, deletes
  and preconditions in a single write (in the typed tier, use the generated
  transaction builder). Use a precondition for invariants such as "don't remove
  the last admin": a must-match filter on the witness relationship.
- **Touch** is an idempotent upsert. **Create** fails if the relationship
  exists. **Delete** removes by tuple identity; use the generated *key* builder
  when the relation requires a caveat or expiration you don't have.
- **Never retry a write automatically.** A failed write may have committed.
  Reconcile with a read, or make the write idempotent (touch), before retrying.
- **Bulk deletion:** bounded delete for a known maximum; all-or-nothing mode to
  reject oversized deletes; delete-to-completion only when partial progress is
  acceptable. It is not atomic, and it reports acknowledged progress on failure.

### Reads, paging and streams

- Reads, lookups and exports page internally. To resume later, keep the
  item's after-result cursor and repeat the **same request and page size**;
  SpiceDB rejects a cursor sent with different arguments.
- Close or exit every stream (native loop/scope cleanup). Don't leave an
  iterator half-consumed in a long-lived object.

### Deadlines, retries and connections

- Unary calls have a 30-second total budget by default, and idempotent reads
  retry transient failures. Applications should keep these defaults. Tools that
  apply their own policy disable the client's (named modes for deadline,
  retries and stream retries) instead of stacking two policies.
- Create **one client per process** and reuse it; close it on shutdown.
- **Remote plaintext requires an explicit opt-in.** Use TLS in production.
- To reuse an existing connection (in-memory, test server), use the
  from-connection constructor. Closing the client leaves that connection open.

### Errors

- Match errors with the library's typed errors or codes, not message text.
  Native errors also work with the ecosystem's standard gRPC status inspection.
- If you forward an error to another party, use the error's *server message*
  field (the server's words, verbatim) rather than the display message.

### Testing

- Unit tests: use the library's **in-memory test double** (same surface as the
  client, SpiceDB filter/precondition semantics, registered check results).
  Build expected errors with the library's error constructor. If you write your
  own fake, use the library's client-side filter matching.
- Integration tests: run SpiceDB in a container
  (`authzed/spicedb serve-testing` isolates data per preshared key) and test
  both the positive and the negative case of every permission you rely on.
- Format relationships for fixtures and logs with the library's tuple syntax,
  which round-trips caveats and expiration.
