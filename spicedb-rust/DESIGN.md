# Rust client design

- **Expose native Rust values through the `spicedb` crate.**
  - The [root design](../DESIGN.md) defines shared semantics, RPC coverage, security, and verification.
  - `client`, `consistency`, `types`, and `error` separate transport, consistency, domain values, and failures; common values are re-exported at the crate root.
  - Requests and options own caller data, use private fields and builders, and never require protobuf or tonic values. Evolving results and enums are non-exhaustive. Domain values derive the usual comparison/debug traits where their data supports them.
  - `raw_proto()` is an authenticated secondary escape hatch with caller-managed deadlines and retries. `RPC_COVERAGE.md` maps every supported nondeprecated RPC to its native wrapper, including experimental Materialize operations. Transport data and protocol-shaped output do not need it: every options type takes `with_call_options(CallOptions)`, and `spicedb::protoconv` exports the conversions.

- **Carry revisions as opaque `ZedToken` values.**
  - Every public revision input and result, consistency strategy, watch resume point, delete result, schema result, permission-set cursor, and Materialize event uses `ZedToken` (or `Option<ZedToken>` for absence).
  - `From<String>`, `From<&str>`, `AsRef<str>`, `Display`, and `into_string()` preserve the exact string contents. Authentication credentials and opaque pagination cursors remain distinct string values.
  - Read requests require explicit `Strategy`; `full()`, `min_latency()`, `at_least(ZedToken)`, and `snapshot(ZedToken)` select consistency. Named optional-token fallback helpers treat absent/empty tokens as their documented fallback; directly supplied empty revision tokens fail validation before RPC.

- **Make execution choices discoverable through enums.**
  - `CheckOptions::with_tracing(TracingMode::{Disabled, Enabled})` and `LookupResourcesOptions::with_debug(DebugMode::{Disabled, Enabled})` default to disabled and map independently to their wire controls.
  - `WatchOptions::with_checkpoints(CheckpointMode::{Exclude, Include})` defaults to Exclude. `with_content(WatchContent::{Relationships, RelationshipsAndSchema})` defaults to Relationships; schema content includes relationship updates as well.
  - `WildcardOption::{Include, Exclude}` selects lookup wildcard behavior. Exact subject filtering uses `SubjectRelationFilter::{Any, Direct, Named(String)}` and rejects unrepresentable filters instead of widening scope.
  - Result facts such as permission grants, checkpoint identity, deletion completion, and cursor progress remain booleans. Native enums prevent unknown option strings or flags from silently changing behavior.

- **Use one request and one extensible options value per operation.**
  - Relationship writes return `WriteResult`; its `revision` field is the native `ZedToken` to use in subsequent consistency or watch requests.
  - `check(PermissionCheck)` performs the singular RPC; `check_bulk(BulkCheckRequest)` preserves input order in chunks of 1,000 and retains each chunk's revision. Bulk item options and mixed consistency strategies are rejected before RPC. Echoed bulk requests must correspond exactly to inputs.
  - Required resources, subjects, permission names, and consistency belong to the request. Check context belongs to checks, never persisted relationships. Call context supplies defaults and item context overrides by key; invalid/nonfinite JSON fails explicitly.
  - `CheckResult` is must-use, retains native recursive optional debug information and missing context, and grants only for `Permissionship::HasPermission`. Unknown and conditional states never grant.
  - An empty transaction is sent: SpiceDB evaluates its preconditions and returns the current revision, so the client does not reject it locally. Watch rejects object types combined with relationship filters because the server does.
  - Relationships contain persisted tuple fields, caveat/context, and UTC expiration. Transactions borrow relationships and store native updates and preconditions. Trees and permission-set events use exclusive native enum variants; unknown updates never become writes or grants.

- **Bound operations and release canceled work.**
  - Unary operations default to one 30-second total budget, configurable by the builder (`default_timeout`) or operation options; `.default_deadline(DefaultDeadline::Disabled)` removes the client default (per-call timeouts and dropping the future still bound the call). The budget includes connection readiness, retries, backoff, chunks, and pages, and propagates remaining time to RPCs.
  - Streams and imports have no default lifetime timeout; an explicit positive timeout covers their full lifetime. Finite paged reads (`read_relationships`, `lookup_resources`, `lookup_subjects`, `export_relationships`, `lookup_permission_sets`) apply the client default deadline to each page, from requesting it to receiving its last item, failing a stalled page with `DeadlineExceeded` ("page deadline exceeded"). It bounds only waiting on the server, never the caller's processing time: reads, resource lookups, exports and permission-set lookups receive a whole page (at most the page size) within its deadline before yielding its items, and a page request carries the earlier of the page and total budgets as its gRPC timeout; the unpaged subject lookup bounds each wait for the server's next message and sends only the total budget. Regression tests use items larger than the HTTP/2 stream window, so the server can only progress as the client reads. An explicit total timeout covers the caller's processing time too and still wins when earlier, and `DefaultDeadline::Disabled` removes the page bound. Watches (`updates`, `watch_permission_sets`) keep no default. Dropping futures or streams releases transport work and upload producers; no detached work survives cancellation.
  - By default, read-only Unavailable/Aborted failures allow three retries with full-jitter backoff from 100 ms (capped at 5 s); ResourceExhausted is not retried by default. `.retry_policy(RetryPolicy)` sets max retries, retryable read codes (a caller may opt into ResourceExhausted), backoff and an `on_retry` callback; `.retries(RetryMode::Disabled)` makes every call one attempt; `.stream_retries(StreamRetryMode::Disabled)` opens streams once. `.operation_retry_policy(Operation, RetryPolicy)` sets the policy for every call of one operation (for example one that reopens a watch that fails before its first event), and `CallOptions::with_retry_policy` for one call; the most specific wins (per call, per operation, client-wide), and either overrides the client's retry modes, including for stream establishment, so one supervised watch can be opened exactly once. `Operation` is a non-exhaustive enum named after the client methods; Rust's per-call option is the non-generic `CallOptions`, so callers abstract over it with ordinary functions. `Transaction::is_idempotent()` (touch-only, no preconditions) is the retry-eligibility rule: a per-operation `Operation::Write` policy retries only idempotent writes and sends the others once, and never-idempotent operations (deletes, delete-all, imports, counter registration and unregistration) reject a retrying per-operation policy when the client is built; a zero-retry policy is allowed anywhere. Mutations are never replayed automatically; only a touch-only `write` without preconditions and `write_schema` may opt in per call, and every other mutation (creates, deletes, preconditioned writes, imports, counter registration, delete-all) rejects a policy with retries as `InvalidArgument` before any request. Streams retry establishment only before exposing data. The client-wide policy (default or configured, whatever `StreamRetryMode`) never reopens a watch (`updates`, `watch_permission_sets`), because a watch reopened without a start revision silently skips changes; only a per-call or per-operation policy opts a watch in to reopening before its first event, and watch otherwise requires explicit resume. A full page whose continuation cursor is missing, empty or equal to the one sent fails reads, lookups and exports with `Internal` rather than re-requesting the page. Likewise a response the client cannot interpret fails with `Internal` (never retried by default; `SpiceDBError::is_client_detected()` is true and `Display` reads "client detected malformed response from server: ...", so it is not mistaken for a server status) instead of being skipped or filled with empty values: a read response or watch update without its relationship, a relationship without its resource, subject or subject object, a check, bulk-check item or lookup result whose permissionship is unspecified (the double never sends one), a lookup result without a resource ID or subject, an expand result without its tree root, or a tree node or debug-trace subject without its object. An unset `oneof` that may be a kind this client does not know (a tree node, a counter result, a permission-set event) stays the documented `Unknown` variant, since prost cannot tell it from an absent one.
  - Clients are cheap Clone, Send, and Sync; independent operations share a channel without a global lock. Raw handles own the channel independently.

- **Preserve exact deletion scope and acknowledged progress.**
  - `delete_relationships(DeleteRequest::new(filter, NonZeroU32))` performs one bounded RPC. `DeleteOptions::with_partial(DeletePartial::Disallowed)` makes it all-or-nothing (the server rejects a delete exceeding the limit); only in that mode may the limit be omitted with `DeleteRequest::server_default_limit(filter)`, otherwise the call fails before any RPC. `delete_all_relationships_non_atomic(DeleteAllRequest::new(filter))` follows completion pages with a separate positive page size (default 1,000) and one total budget; `DeleteAllOptions::with_progress` is called after each acknowledged batch with the cumulative count, revision and cursor.
  - Preconditions apply to every page. Missing server cursors resume with the same filter; zero-count partial pages fail as nonprogress. Unknown completion states fail and never authorize another delete.
  - `DeleteResult` retains typed revision, count, completion, and optional cursor. Errors after acknowledged pages carry cumulative confirmed progress and the original typed cause, including malformed later responses.
  - Multi-page deletion is not atomic. An unacknowledged mutation may have committed and is never replayed automatically. Future drop cannot return progress; resumable cancellation uses bounded calls and persisted results.

- **Preserve native RPC data and diagnostics.**
  - Read/export/lookup streams support native context, supported limits and cursors, page sizes, and total timeouts. Every page repeats the caller's consistency and page size (SpiceDB hashes both into the cursor, which pins later pages to the first page's revision); total limits are enforced client-side, never by shrinking the last page. `read_relationships` yields `ReadRelationship { relationship, after_result_cursor, read_at }`, `export_relationships` yields `ExportedRelationship { relationship, after_result_cursor }` (shared by a response's items; exports have no read-at), and `LookupResource` carries `after_result_cursor` and `looked_up_at`. Resume with the options' `with_cursor` and the same request and page size. `ReadRelationshipsOptions`/`LookupResourcesOptions::with_paging(Paging::SingleRequest)` sends exactly one request like the raw API: its limit is the total limit or unbounded (0), the page size is ignored, and no follow-up page is fetched. LookupSubjects has no fabricated cursor. Wildcard exclusions and conditional permissions remain visible; results are not deduplicated.
  - Import sends batches of 1,000 relationships per message (`ImportRelationshipsOptions::with_batch_size`); one call is one stream and one transaction. When the server aborts the stream, its final status (for example `AlreadyExists`) is returned. Cancellation and producer errors propagate. Watch preserves updates, typed revisions, and checkpoint/schema events. Reflection/diff preserve native schema structures; counters preserve explicit still-calculating state.
  - Materialize wrappers preserve revisions, exclusive set/member changes, all cursor fields, completed/rebuild/schema events, file URLs and UTC timestamps. Unsupported consistency controls are not invented.
  - Typed errors retain status categories, structured reason/domain/metadata, and original sources. Local validation and timeouts use native categories without fabricated server statuses; `server_message()` is the server's message verbatim (`None` for local errors).

- **Require an explicit transport security policy.**
  - `new_system_tls(endpoint, token)` and `builder(endpoint, token)` use native trust roots. Custom CA injection and client identity are not currently supported.
  - `new_plaintext(endpoint, token, RemoteCredentialsPolicy::LoopbackOnly)` permits transport-parsed loopback. `RemoteCredentialsPolicy::AllowInsecureRemote` explicitly permits transmitting credentials without TLS to remote hostnames or IP addresses.
  - The normal builder offers `.plaintext().remote_credentials_policy(RemoteCredentialsPolicy::AllowInsecureRemote)`. The policy is available without raw access and defaults to LoopbackOnly.
  - Endpoint and token validation reject unsupported gRPC targets (`dns:`, which promises client-side load balancing tonic does not do, `ipv4:`, `ipv6:`, `unix-abstract:`, `vsock:`, `xds:`, and `unix:` on platforms without Unix sockets), remote plaintext without opt-in, and invalid credentials before channel creation; secrets never appear in diagnostics.
  - Endpoints are `host:port`, `http://host:port` or `https://host[:port]`. With `builder` the URL scheme selects plaintext or TLS (a `host:port` endpoint is TLS unless `.plaintext()`); `new_plaintext`, `.plaintext()` and `new_system_tls` require a scheme to agree. The scheme is never prefixed a second time. The endpoint's form is validated in full before the remote credentials policy: any other scheme, a disagreeing one, a path, query or fragment, userinfo, an empty or non-numeric port, a plaintext endpoint without a port (an `http://` URL or a bare host such as `localhost` or `::1`; the error names `host:50051`), or an invalid host fails at construction with `InvalidArgument` naming that problem and the accepted forms, so no endpoint builds a client whose every call fails and the policy refusal (which names the endpoint) is only ever about a well-formed remote host, judged by its parsed host. A TLS endpoint without a port (URL or bare host) uses 443. A connection failure at construction is `Transport` displaying `connecting to <endpoint>: <cause>`, the distinct messages along the source chain (refused, DNS, TLS), with `source()` unchanged.
  - On Unix platforms `unix:/path`, `unix:///path` and `unix:relative` dial that socket through a connector (never as a URI host, which would resolve the DNS name `unix`): plaintext only (with `builder` the scheme selects plaintext; TLS is `InvalidArgument`), local so no remote-credentials opt-in, and verified by a live call to SpiceDB over a socket.
  - Plaintext connects lazily by default and TLS eagerly. `.connect_mode(ConnectMode::Eager)` connects during `build`, so a wrong or unreachable endpoint fails at startup with `Transport`; `ConnectMode::Lazy` lets either transport start without SpiceDB. `ConnectMode::Eager` is the startup readiness check; there is no separate awaitable ready call on a lazy client, because a lazy tonic `Channel` dials only when a request is dispatched (its `poll_ready` checks buffer capacity, not the connection), so one would have to send an RPC or open a second connection that is not the client's.

- **Make completion deletion explicitly non-atomic.**
  - `delete_all_relationships_non_atomic` commits each batch transactionally. The whole operation is non-atomic: completed batches remain committed if a later batch fails.
  - `DeleteResult.revision` carries the native revision; failure progress preserves the last acknowledged revision and cumulative count.
  - Each nonempty server cursor becomes the next batch cursor. Empty or absent cursors retain the filter-based fallback; results and failure progress retain the last acknowledged cursor.

- **Verify observable contracts.**
  - Regression tests cover exact token conversion, enum wire mappings and defaults, strict bulk correspondence, safe unknown values, total budgets, transport cancellation, upload producer failures, typed diagnostics, exact filters, and deletion progress.
  - Security tests exercise parsed endpoints and opt-in behavior; gated integration tests complete real TLS handshakes. Examples assert behavior and are reconciled with their runner.
  - Run cargo formatting, tests, all-target build, clippy, documentation checks, and coordinated real-server examples. The root design governs cross-language compatibility and CI conventions.

- **Keep conditional lookup results distinct from unconditional grants.**
  - LookupResources preserves all permissionships by default, including conditional results. The optional `LookupPermissionshipFilter` selects only exact unconditional grants with `LookupPermissionshipFilter::HasPermissionOnly`.
  - Filtering happens client-side before yielding. Limits count yielded matches; skipped rows still advance cursors and page counts.
  - Conditional and unknown permissionships must never enter unconditional resource ID lists.

- **Expose native relationship filters for watch streams.**
  - `WatchOptions::with_filters` sends each native relationship filter to the server with OR semantics, including resource IDs, relations, and subject filters. Empty filters watch all relationships.
  - Object types and relationship filters are mutually exclusive and rejected locally when combined. Filter values are captured before streaming and preserve existing cancellation and resume behavior.

- **Satisfy every root adoption rule explicitly.** How this crate meets each cross-cutting requirement in the root design:
  - *Single protocol copy / legacy bridge:* not applicable. prost has no process-global descriptor registry, so another crate's generated `authzed.api.*` types coexist as distinct Rust types without load-time conflicts, and no official `authzed-*` Rust library exists to alias. See `../proto-clients/spicedb-rust-proto/DESIGN.md`.
  - *Existing-connection constructor:* `SpiceDBClient::from_channel(channel).token(..).build()` over any tonic `Channel` (in-memory `connect_with_connector`, embedded SpiceDB). `Channel` is a shared handle: the caller keeps ownership and dropping the client never closes it. Deadline and retry settings apply; endpoint, TLS and remote-credential settings do not. Rust has no `close`; drop releases only the client's clone. A tonic channel carries no credentials, so the bearer token is an explicit, optional builder setting; with no token, a caller may send `authorization` through `CallOptions`.
  - *Per-call transport options and response metadata:* every options type has `with_call_options(CallOptions)`: `with_request_metadata(MetadataMap)` is sent on every RPC the operation makes, and `with_response_metadata(ResponseMetadata)` captures the last RPC's headers and trailers (tonic merges unary trailers into the response metadata, so both accessors return that map for unary calls; failures capture the status metadata). This is the route to data pre-1.30 servers send in trailers. Request extensions are not exposed: they only reach local tower layers, and the client's channel stack has none a caller can add.
  - *Exported protocol conversions:* `spicedb::protoconv` converts tokens, objects, subjects, relationships, filters, preconditions, updates, transactions (to `WriteRelationshipsRequest`) and consistency in both directions, and check results (with traces), lookups, expand trees, read items and write results to their protocol responses. Conversions to responses reproduce the server's wire shape: `check_bulk_to_proto(&BulkCheckRequest, &[CheckResult])` rebuilds a whole bulk response (per-item errors as the server's own `google.rpc.Status`, call context merged into items as sent), `check_request_to_proto` converts one item, `lookup_subject_to_proto` also fills the deprecated top-level fields SpiceDB still sends, and `reflect_schema_result_to_proto` converts reflection; tests round-trip mock server responses. Protocol-to-native conversions validate and fail with `InvalidArgument`.
  - *SpiceDB 1.30+ floor:* only 1.30+ behavior is native (for example singular check traces in the response body); older servers' trailer data is reachable through `ResponseMetadata`.
  - *Error interop, constructor and server message:* `SpiceDBError::code()` returns the matching `tonic::Code` for every error, including local validation (`InvalidArgument`), elapsed client deadlines (`DeadlineExceeded`), transport failures (`Unavailable`) and constructed errors. `From<SpiceDBError> for tonic::Status` (and `to_status()`) returns the original status for server errors and a new status with the same code otherwise; `From<tonic::Status> for SpiceDBError` maps raw statuses; `spicedb::error::code_of(&dyn Error)` classifies native errors, raw statuses and source chains. `SpiceDBError::new(code, message)` builds an error indistinguishable from a mapped server error. `server_message()` is the server's message verbatim. `BulkItem` and `DeleteProgress` wrappers delegate `code()`, `status()`, `server_message()` and `to_status()` to their cause, so a converted status carries the server's message once; only `Display` adds the item or progress prefix.
  - *Filter matching:* `Filter::matches(&Relationship)` with server semantics (type, ID or prefix, relation, subject type/ID, `Any`/`Direct`/`Named`); filters the protocol rejects match nothing.
  - *In-memory test double:* `spicedb::testing::InMemorySpiceDB` (feature `testing`) serves `PermissionsService` over an in-memory channel and returns a real `SpiceDBClient`, so its surface is the client's surface. It models writes (preconditions, `CREATE` conflicts with SpiceDB's reasons, atomicity, empty writes), filtered paged reads and exports with cursors, limits and the export filter, atomic imports (`ALREADY_EXISTS` adds nothing), bounded and all-or-nothing deletes, `SchemaService` read/write of the schema text, check resolution in the root order (a result registered with `set_check_result` for the exact question; then a resolver from `set_check_resolver`, which receives the native `PermissionCheck` as sent, including merged caveat context, returns a `Resolution` or `None` to decline, never fails, runs without the store lock, and has a one-line `grant_all`; then the stored relationships, where an unexpired relationship on the resource whose relation is the permission's name and whose subject matches exactly or as a wildcard over a direct subject grants, a caveated match only conditionally and an uncaveated match winning; otherwise `NoPermission`), `LookupResources` and `LookupSubjects` over the stored relationships (objects of the requested type in first-appearance order as resource or subject, those check resolution grants, conditional results with their missing context; lookup-resources cursors are `cursor_after(n)` counting granted results, so the client-side permissionship filter, limits, page sizes and resume behave as against SpiceDB; lookup-subjects reports a stored wildcard as `*`, honors the wildcard option, subject relation and limit, and has no cursor, like the client), and a registered reflection (`set_reflect_schema_result`; schema result types derive `Default` so tests can build them), and sends `set_response_metadata` headers on every response. It serves every service the client calls (permissions, schema, watch, experimental, Materialize), so every client method reaches it; RPCs it does not model are recorded, consult the fault hook, and otherwise return `UNIMPLEMENTED`, which the client maps like SpiceDB's own status. Rust needs no separate client trait for this: the double's surface is the real `SpiceDBClient`, and a crate test calls every client method (one per `Operation`, matched exhaustively so a new operation must be added) against the double, asserting it is recorded, consults the hook, and fails as `UNIMPLEMENTED` when unmodeled. Because the double sits behind a real client, its errors have the real client's codes and shape (server errors mapped with `server_message`, local validation raised before any request) and every option is honored as sent on the wire, so no option-resolving API is needed. Every RPC is recorded (`calls`, `calls_of(Operation)`) as a `Call` with its operation, per-operation index, protocol request (`request::<T>()`) and request metadata: options are recorded in the form they reach the server, which is how Rust represents them to a double behind a real client (a client retry or page is its own recorded call). `set_fault_hook` runs before any RPC (`FaultStage::Call`), before each import batch (one message, so the call's batch size; `Fault::batch` holds its relationships), before an import commits, and before each read, export or lookup item; `fail_next(Operation, Status)` fails one RPC. Successful responses are shaped through the natural hook for each operation: registered results and the check resolver for checks and lookups, the stored relationships for the rest. A failed write or import applies nothing. Read and export cursors count matching relationships, and `testing::cursor_after(n)` builds the cursor the double puts on item `n` (a stable decimal format). `set_read_schema_revision(SchemaRevision::Omitted)` makes schema reads report no revision (the client returns an empty `ZedToken`). `testing::server_error` and `server_error_with_reason` build SpiceDB-shaped statuses, which the client maps exactly as it maps the server's.
  - *Panicking constructors:* not provided. Rust convention is a `Result` and an asserting `.expect()` at the call site, which names the failing constant; `must_*` twins would double the constructor surface for no gain. Parsing is one call (`"document:a#viewer@user:alice".parse::<Relationship>()`), and `ObjectRef`/`SubjectRef` implement `FromStr` too.
  - *String, log and serialization forms; transaction length:* `Display` on `ObjectRef` (`type:id`), `SubjectRef`, `Relationship` (full tuple), `Filter` (zed-like with `*`), `SubjectRelationFilter`, `Update`, `Precondition`, both operation enums, `Transaction`, `ReadRelationship` and `ExportedRelationship`; derived `Debug` is the structured log form; the `serde` feature derives `Serialize` for tokens, refs, relationships, filters, updates, preconditions and transactions. `Transaction::len()`/`is_empty()` do not copy.
  - *Short relationship accessors:* `resource_type()`, `resource_id()`, `subject_type()`, `subject_id()`, `subject_relation()`.
  - *Full tuple syntax and copy helpers:* `Relationship::from_tuple`/`FromStr` and `Display` cover `[caveat]`, `[caveat:{json}]` and `[expiration:RFC 3339]` (UTC, trailing zeros trimmed, keys sorted), checked against SpiceDB v1.56.2's `tuple.String` output. `with_resource`, `with_subject` and `with_relation` copy a relationship. Protobuf numbers are doubles; integral values read back as JSON integers.
  - *Bulk item-error mode:* `CheckOptions::with_bulk_item_errors(BulkItemErrors::Returned)` returns every item; a failed item carries `CheckResult::error` (`SpiceDBError::BulkItem` with the absolute index) and `Permissionship::Unspecified`, and `has_permission()` is false. The default `BulkItemErrors::Fail` fails the call.
  - *Default-deadline disable mode:* `DefaultDeadline::Disabled` (above). Zero durations are rejected, never a magic value.
  - *Retry policy, disable and stream-establishment retry:* `RetryPolicy`, `RetryMode::Disabled`, `StreamRetryMode::Disabled` (above).
  - *Import server status on abort and batch size:* tonic already resolves a client-streaming call with the server's final status rather than an end-of-stream send error; a test with a server that aborts mid-stream, and a live duplicate import, pin it. Batch size: `with_batch_size` (above).
  - *Paging cursors, read-at, resume and argument stability:* above. This fixed the same page-two bug as Go: the pager switched later pages to `snapshot(read_at)` and shrank the last page's limit, which SpiceDB rejects.
  - *Watch schema changes:* `WatchOptions::with_content(WatchContent::RelationshipsAndSchema)`, combinable with `with_checkpoints(CheckpointMode::Include)`; `WatchEvent::schema_updated`.
  - *All-or-nothing delete and delete-all progress:* `DeletePartial::Disallowed`, `DeleteRequest::server_default_limit`, `DeleteAllOptions::with_progress` (above).
  - *MIGRATION.md:* there is no official `authzed-*` Rust predecessor, so `MIGRATION.md` covers the predecessor projects actually have: vendored protos, a tonic `build.rs`, a hand-written client and a mock server. It opens with the Requirements section (Rust, tonic/prost generation, tokio, TLS, SpiceDB floors), explains consuming the unpublished crate, and has the legacy-to-new member table.
  - *README:* `README.md` covers installation before publication, a first call, and links to DESIGN, MIGRATION and this crate's AI integration guide.
  - *Direct subjects:* `SubjectRef::direct(object)` and `From<ObjectRef> for SubjectRef` are infallible, and the subject relation `...` means a direct subject in `SubjectRef::new`, filters (`SubjectRelationFilter::Named("...")` is `Direct`) and `LookupSubjectsOptions::with_subject_relation`.
  - *Package name:* the package and library stay `spicedb`, the name an official client should own on crates.io (`spicedb-client` and `spicedb-rust` belong to unrelated crates there). A project whose own crate is also named `spicedb` keeps both during a phased migration with Cargo's `package = "spicedb"` rename under another dependency key; MIGRATION.md documents it, including Cargo's refusal of two path or git packages with the same name and version.
  - *Dependency floors:* tonic is used without default features (`codegen`, `channel`); tokio only with `macros`, `rt`, `sync`, `time`; chrono without default features. Server, router, tower and hyper-util are optional behind `testing`, serde behind `serde`. Floors for chrono, futures, rand, serde_json and async-stream were verified by pinning them in the lockfile and running the suite. The transport targets the current tonic generation (tonic, tonic-types, tonic-prost and prost 0.14, tower 0.5), as the root rule on floors and framework targets requires: an application on tonic 0.14 links one tonic and prost, so `tonic::Status::from(SpiceDBError)`, `from_channel` with its own `Channel` and `spicedb::tonic` interoperate. The generation moves as one unit; tokio is floored by tonic's own requirements. Build and test tooling stays in dev-dependencies or the Go Magefile.
  - *Typed generation:* not applicable; `spicedb-gen` has no Rust backend.
  - *AI integration guide:* `AI_INTEGRATION_GUIDE.md`, linked from the crate documentation; its snippets are compile-checked against the current API.
